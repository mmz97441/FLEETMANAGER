Les tests sont configurés dans GitHub Actions, avec le build serveur et les audits de dépendances. Les fichiers `functions/lib` sont aussi recompilés automatiquement avant un déploiement Firebase.

## Reproduire les contrôles

Depuis la racine, avec Node 22 et Java 21 :

```sh
npm ci
npm ci --prefix functions
npm run typecheck
npm test
npm run build
npm run build --prefix functions
npm install --global firebase-tools@15.15.0
JAVA_TOOL_OPTIONS='-Duser.language=en -Duser.country=US' firebase emulators:exec --project demo-fleet-production-audit --config firebase.test.json --only firestore,storage 'npm run test:emulated'
npm audit --audit-level=moderate
npm audit --prefix functions --audit-level=moderate
```

La configuration de test fixe Firestore sur `127.0.0.1:8189`, Storage sur `127.0.0.1:9199`. Les scripts effacent uniquement les données de ce projet de démonstration dans les émulateurs. Ne pas remplacer cet identifiant par celui d’un vrai projet.

## Conditions avant publication

1. **Accès et configuration réels.** L’alias public observé est `https://delivrex.vercel.app`, associé au projet Firebase `fleet-genius-app`. L’accès au projet, les permissions de publication, les index et la compilation des règles ont été confirmés le 10 septembre avec la CLI. Le contrôle `firebase deploy --dry-run` a réussi. Les secrets, les API externes, la réception effective des emails et la recette terrain doivent être vérifiés séparément.
2. **Données historiques.** Vérifier doublons d’emails et de références colis, sociétés de même nom, identifiants utilisateur hérités, affectations existantes et soldes de congés. Pour une ancienne absence approuvée sans `balanceDebit`, la durée ne permet pas de connaître le débit réel : l’ancien code ramenait le solde à zéro en cas de dépassement. Le serveur interdit donc les changements affectant ce débit et la suppression avant rapprochement comptable. Une modification sans effet sur le solde conserve le débit inconnu ; un montant envoyé par le navigateur ne peut pas le valider. Les demandes nouvelles et les débits déjà enregistrés continuent à être traités en transaction. Les corrections ne réparent pas automatiquement des preuves déjà perdues.
3. **Publication coordonnée.** Mettre en place les fonctions et index en recette, puis publier frontend et règles ensemble dans une fenêtre contrôlée. Les anciens clients qui écrivent directement invitations, absences ou emails ne sont plus compatibles avec les nouvelles règles. Terminer les saisies des chauffeurs et leurs synchronisations avant la bascule ; ne pas déployer uniquement le frontend.
4. **Invitations et secrets.** Réémettre les anciennes invitations depuis le nouveau serveur. Configurer `APP_URL`, le projet GMPRO et, si utilisé, Gemini côté serveur. Ne jamais ajouter de secret Gemini à une variable `VITE_*`. Le conseiller IA échoue explicitement s’il n’est pas configuré.
5. **Recette terrain.** Valider sur les téléphones utilisés : photographie/signature, GPS refusé, coupure réseau pendant les preuves, fermeture puis réouverture de l’application, stockage saturé, réception d’emails et notifications. La file durable couvre la validation des livraisons et leurs preuves ; elle ne transforme pas les autres transactions en opérations hors ligne. L’effacement des données du navigateur peut supprimer des envois encore locaux.
6. **Charge et exploitation.** Mesurer les abonnements aux historiques avec le volume réel, le coût de `client_tracking` et l’autonomie GPS. Vérifier sauvegarde/restauration et supervision des erreurs avant d’ouvrir à tous les utilisateurs.

Les résultats de compilation et des tests ne suffisent pas à attester la publication. L’état effectif de la fusion et des déploiements est à vérifier dans GitHub, Firebase et Vercel ; une publication doit conserver une sauvegarde et les versions précédentes des règles.
